# DAV file versions

This implementation belongs to CompuMaster.Ocs and is additive. Existing OcsClient download/upload methods and standalone consumers keep their behavior. DavFileVersionClient accepts a caller-owned IWebDavClient, an explicit observed protocol and the DAV root. It provides synchronous wrappers and native asynchronous operations; no general DMS async API is introduced.

| Server | Listing and download | Restoration | Individual removal | Metadata |
| --- | --- | --- | --- | --- |
| Nextcloud | PROPFIND `versions/USER/versions/FILEID/`, GET selected historical child | MOVE selected child to `versions/USER/restore/target` | DELETE selected child, only when authenticated `files.version_deletion` is true; unknown/false rejects locally | DAV timestamp, length, ETag, media type; optional `nc:version-author` and `nc:version-label` |
| ownCloud Classic | PROPFIND `meta/FILEID/v/`, GET selected child | COPY to the current file, conditional on current ETag | Unsupported by this client; no individual DAV removal contract is established | DAV metadata; optional `oc:meta-version-edited-by`, `oc:meta-version-edited-by-name`, `oc:meta-version-tag` |
| ownCloud Infinite Scale | The official Web client uses `meta/RESOURCEID/v/`; IDs are opaque | The official Web client uses COPY to its resolved current-file DAV address | Unknown upstream per-resource behavior; unsupported by this client | DAV metadata; optional fields remain unknown when absent |
| Generic WebDAV | No built-in version workflow | Unsupported | Unsupported | DeltaV is not implemented |

Authenticated `files.versioning` is separate from protocol recognition, permissions and the presence of retained versions. Callers must establish enabled versioning before presenting this workflow. Missing/disabled namespaces, 401/403 and other errors remain exceptions, never empty history. Only a valid collection with no historical children means empty/pruned history. Nextcloud's synthetic current entry is excluded when its DAV modification time matches the current file, following the official client; its historical GET can otherwise return 404. Unknown modification metadata remains unknown, and version IDs remain opaque. This rule is not applied to ownCloud protocols. Per-file/backend authorization still decides restore/removal; advertised deletion does not prove every storage backend supports it. An administrator's retention/cleanup command is not an individual consumer API.

Listing resolves the stable current file ID from `oc:fileid` (or `oc:id`) and binds versions to that identity and the listing client. Metadata IDs remain distinct from labels/timestamps. Restore and removal revalidate the current file before mutation. Classic/Infinite Scale COPY additionally requires a strong current ETag and a DAV destination condition to avoid overwriting a concurrently replaced file. Nextcloud restore targets file identity through its special namespace. Re-list current metadata and history after a mutation; do not assume that restore deletes a historical version or returns a new version ID. A missing/renamed path or changed file ID fails rather than creating/replacing another file.

Download streams the exact listed version to a caller-owned writable stream. No complete-file buffering occurs; active request/copy cancellation is passed through, partial output remains the caller's responsibility, and the response stream is always disposed. Never automatically replay an ambiguous mutation after cancellation/transport failure. Transport ownership and origin/redirect restrictions remain with the caller; untrusted hrefs, cross-origin children, nested/duplicate IDs and foreign-client snapshots are rejected.

Local verification: 37 isolated version wire/stream cases and 19 chunk/result-parser regressions pass on net8.0 and net48. In a coordinated exclusive window on 2026-10-12, Nextcloud 34.0.3 and ownCloud Classic 10.15.2 passed live original-byte download, restore, stable file identity and refreshed-history checks on Windows/net8.0 and Windows/net48. Nextcloud additionally passed advertised individual version removal; ownCloud rejected unsupported removal locally. Exact owned files and test scopes were removed and their absence verified; configured permanent test roots were preserved. Infinite Scale, versions-disabled/read-only server configurations and broader retention policies remain unverified.

The `RemoteFileVersions` fixture is disabled unless `OCS_VERSION_TESTS_EXCLUSIVE=1` is explicitly set after coordinating exclusive access, including cross-repository CI and local sessions. It requires the standard-user instance-root URL, username and password under the existing `TEST_NEXTCLOUD.STANDARDUSER_*` and `TEST_OWNCLOUD.STANDARDUSER_*` environment settings. The serialized Build and Test workflow offers `cloud_versions_only` for this focused acceptance; do not dispatch it during another cloud reservation. If both mode flags are selected, `isolated_only` takes precedence and neither selects nor enables server acceptance; all four mode combinations are checked automatically. Ordinary runs do not opt into the new live fixture. Release publication uses the validated numeric release tag as the package version and rejects branch dispatch publication.

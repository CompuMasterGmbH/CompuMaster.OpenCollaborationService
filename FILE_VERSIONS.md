# DAV file versions

This implementation belongs to CompuMaster.Ocs and is additive. Existing OcsClient download/upload methods and standalone consumers keep their behavior. DavFileVersionClient accepts a caller-owned IWebDavClient, an explicit observed protocol and the DAV root. It provides synchronous wrappers and native asynchronous operations; no general DMS async API is introduced.

| Server | Listing and download | Restoration | Individual removal | Metadata |
| --- | --- | --- | --- | --- |
| Nextcloud | PROPFIND `versions/USER/versions/FILEID/`, GET selected child | MOVE selected child to `versions/USER/restore` | DELETE selected child, only when authenticated `files.version_deletion` is true; unknown/false rejects locally | DAV timestamp, length, ETag, media type; optional `nc:version-author` and `nc:version-label` |
| ownCloud Classic | PROPFIND `meta/FILEID/v/`, GET selected child | COPY to the current file, conditional on current ETag | Unsupported by this client; no individual DAV removal contract is established | DAV metadata; optional `oc:meta-version-edited-by`, `oc:meta-version-edited-by-name`, `oc:meta-version-tag` |
| ownCloud Infinite Scale | The official Web client uses `meta/RESOURCEID/v/`; IDs are opaque | The official Web client uses COPY to its resolved current-file DAV address | Unknown upstream per-resource behavior; unsupported by this client | DAV metadata; optional fields remain unknown when absent |
| Generic WebDAV | No built-in version workflow | Unsupported | Unsupported | DeltaV is not implemented |

Authenticated `files.versioning` is separate from protocol recognition, permissions and the presence of retained versions. Callers must establish enabled versioning before presenting this workflow. Missing/disabled namespaces, 401/403 and other errors remain exceptions, never empty history. Only a valid collection with no children means empty/pruned history. Per-file/backend authorization still decides restore/removal; advertised deletion does not prove every storage backend supports it. An administrator's retention/cleanup command is not an individual consumer API.

Listing resolves the stable current file ID from `oc:fileid` (or `oc:id`) and binds versions to that identity and the listing client. Metadata IDs remain distinct from labels/timestamps. Restore and removal revalidate the current file before mutation. Classic/Infinite Scale COPY additionally requires a strong current ETag and a DAV destination condition to avoid overwriting a concurrently replaced file. Nextcloud restore targets file identity through its special namespace. Re-list current metadata and history after a mutation; do not assume that restore deletes a historical version or returns a new version ID. A missing/renamed path or changed file ID fails rather than creating/replacing another file.

Download streams the exact listed version to a caller-owned writable stream. No complete-file buffering occurs; active request/copy cancellation is passed through, partial output remains the caller's responsibility, and the response stream is always disposed. Never automatically replay an ambiguous mutation after cancellation/transport failure. Transport ownership and origin/redirect restrictions remain with the caller; untrusted hrefs, cross-origin children, nested/duplicate IDs and foreign-client snapshots are rejected.

Local verification: 25 isolated wire/stream cases pass on net8.0 and net48; the library builds netstandard2.0/net48/net8.0 with zero warnings/errors. These checks contact no real server. Live ownCloud/Nextcloud/Infinite Scale compatibility, versions-disabled/read-only configurations and server-specific retention semantics remain unverified pending authorized access and a coordinated exclusive test window.
